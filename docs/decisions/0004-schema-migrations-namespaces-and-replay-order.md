# ADR 0004：表结构迁移、命名空间与消息回放顺序

- 状态：Accepted（回放顺序由 ADR 0005 补充）
- 日期：2026-09-30
- 关联：ADR 0001（决策 3、5）、红线 6；taifeng ADR 0008、ADR 0025

## 背景

第一版 Postgres 与 Redis 后端落地时，有四件事需要定下来：表怎么建、数据怎么隔离、连接谁来管、消息按什么顺序回放。

最后一件是实现中撞出来的：把消息镜像挂到内核 `EnginePool` 上真跑，发现镜像里助手的回复排在了用户提问之前。原因是内核以并发任务触发 `IndexHook`，两次写入谁先落库不确定；按自增主键回放得到的是落库顺序，不是对话顺序。

## 决策

1. **表结构只经迁移变更。** 迁移脚本是随包分发的 SQL 文件，按组件、按版本号顺序执行，执行记录连同脚本摘要记在库里。存储实现不建表不改表，只提供 `check_schema()` 供宿主在启动时核对。
2. **迁移按组件独立计版本。** `core`（线程目录与消息）和 `memory`（向量记忆，依赖 pgvector 扩展）各记各的，不用向量记忆的宿主不需要装扩展。
3. **一次迁移是一个事务，事务开头取咨询锁。** 任何一步失败全部回滚；多个实例同时启动时只有一个真正执行。
4. **已发布的迁移脚本不得修改。** 执行前核对摘要，对不上就拒绝继续。
5. **不自带迁移框架。** 迁移逻辑是一个两百行的模块，只依赖 asyncpg。
6. **隔离靠命名空间，命名空间由宿主给。** Postgres 是 `schema` 加表名前缀，Redis 是键前缀，向量记忆另有 `scope`。本仓不认识租户，怎么划分由上层决定。
7. **标识符按字符集校验。** schema、前缀、表名会拼进 SQL，只接受小写字母、数字、下划线；所有取值一律走参数绑定。
8. **连接池由宿主创建并注入，本仓不关闭它。** 连接数上限、超时、重试、追踪都是宿主已有的基础设施。
9. **JSON 列经 `text` 中转读写**，不依赖宿主连接池上是否注册了 jsonb 编解码器。
10. **回放顺序是 `(position, seq)`。** `position` 由写入方在调用进入时、第一个 `await` 之前同步取得（纳秒时间戳，进程内严格递增）；同一批消息共用一个 `position`，批内按自增的 `seq`。调用进入的先后不受并发写入影响。
11. **消息镜像是视图，不是主存。** `PostgresMessageMirror` 写入失败不影响会话；镜像与节点本地 JSONL 不一致时以后者为准。

## 否决的方案

- **首次使用时自动建表**：省了一步部署，但多实例同时启动会竞争建表，线上库的表结构变更也脱离了审阅。
- **引入 Alembic**：功能齐全，但会带进 SQLAlchemy 依赖，与「后端客户端走 extras、核心零依赖」不符，也用不上它的自动生成。
- **按消息的 `created_at` 回放**：消息对象的创建时刻和它被追加的时刻不是一回事——工具调用在采样时创建、在工具执行完之后才追加，按创建时间排会把它排到工具意图记录之前。
- **镜像里串行化每个线程的写入**：钩子到达的顺序本身已经被并发打乱，串行化只是把错误的顺序固定下来。

## 后果

- 宿主的部署流程里要多一步 `taifeng-stores-migrate`。
- 向量维度在迁移时定死，换嵌入模型要新建命名空间重新沉淀。
- 会话被另一个节点接管时，`position` 靠系统时钟衔接；节点之间时钟偏差大于两次写入的间隔时，接管点前后的少量镜像消息可能错位。
- Redis 目录带过滤条件的列表是顺序扫描，代价随线程总数增长。
